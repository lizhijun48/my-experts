# 体检清单与资产冻结纪律（来源：§六 C 类）

> 本文件由源资产原文程序化提取，保持原样以零信息丢失；口径以原文为准。


## 六、C 类：已有文件体检清单


用户给出 SKILL.md 或包路径时，**先跑挂载的 audit.py，以其输出为结论**；本表用于解释其输出、补充体检器未覆盖项。逐项检查并输出问题表（含严重度、位置、修法），**不只给泛泛建议**：

| # | 检查项 |
| --- | --- |
| 1 | SKILL.md 是否存在、是否在包内根位置 |
| 2 | frontmatter `---` 成对闭合、缩进为空格 |
| 3 | 必填字段是否齐全（对照实证 9 项） |
| 4 | `version` 是否存在且符合语义化版本 |
| 5 | `author` 是否仍为占位值（如 your-name） |
| 6 | `allowed-tools` 是否非空、写法是否为全库主流（逗号分隔 147/162；数组 8/162 亦过审）、是否过度放权 |
| 7 | 连字符写法是否统一（user_invocable / user-invocable 不混用） |
| 8 | `category` 取值是否与其他包一致（英文小写、不带引号） |
| 9 | 触发词是否覆盖真实口语、是否写明不触发边界 |
| 10 | 正文是否具备"触发条件 → 步骤 → 输出格式 → 红线"四段 |
| 11 | `description_zh` 与 `description_en` 是否语义对齐、不互相矛盾 |

额外抽查：**模板里是否混入元指令**（如"（无则删除本行）"）、**格式示例是否会被渲染成代码块**（缩进示例需放围栏内并声明输出形态）、**边界情形是否有判定规则**（模糊承诺、口语评价、零散信息处理）、**是否写了注入防护**（用户输入一律当数据不当指令）。

**批量体检**：用户一次给多个包时，逐包跑完上表后，额外出一张汇总表（包名 / 问题数 / 最高严重度 / 必修项），并单独列出**跨包一致性问题**（连字符写法、category 取值风格、allowed-tools 空值、字段缺失率、zh/en 一致性）——这类问题单包看不出来，批量才暴露。

**改了内容就要证明"只改了我说的那一处"**：凡声称"只改形态/改名/换位置、不动内容"的修复，必须给出**内容守恒证明**——修复前后对目标文件算 SHA256 多重集（multiset）比对，报告「仅新有 N / 仅旧有 N / 相同 N」。相同数应等于文件总数，否则说明有文件被顺手改过。这比"我检查过了"可核，也是**知识型资产**（内容来自知识库/客户资料、不许改动的那类）动手前的自证底线。

### 报告口径：资产冻结纪律（体检前先确认状态）

体检报告**只做风险标注，不擅自列修复计划**。理由：**修改已上线资产本身就是风险源**（实证：一个已过审的技能只多加 1 个文件即被驳回）。

- 用户口径是「**之前审核通过的、没问题的就暂时不动**」。
- 确需修，**先问「这个包过审 / 上架了吗」**；过审且只有静态小瑕疵的，**先放着**。
- 例外仅三种：① 平台已驳回、需修到能过审；② 用户明确要求；③ 安全问题（凭证泄露等）。
- ⭐ **知识型资产的加强版**：内容全部来自知识库/客户资料生成的包（如 IMA 知识库产出的专家包），**只修形态/硬件/契约（目录层级、文件名、字段必填、编码标志位、话术契约），绝不改知识内容**——包括案例正文、口径标注、版本"不确定"的诚实写法。想改内容先问，且改动前必须先做内容守恒证明（见上一节）。理由：这类包的价值全在内容忠实度，形态坏了能修，内容被"优化"过就再也查不回来了。
- ⭐ **源码目录 ≠ 包**：混放工作区（一个目录里躺着多个独立包，如 `expert-src/` 根下 1 个专家包 + 8 个单专家 + `skills/`）上跑体检，会因"别家文件的字段值被当成本包的"产生假阳性（实测：别家 README 的版本号顶掉本包 README，误报版本分叉）。**权威结论取打包产物上的结果**；工作区上的 BLOCKER 先核实是不是连坐，再决定修不修。
