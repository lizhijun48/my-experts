## 一、严重度定义

| 级别 | 判定含义 | 扣分 |
|---|---|---|
| BLOCKER | 会被打回，或会误导使用者按不存在的东西作答/交付 | 20 |
| MAJOR | 质量硬伤，交付前应修 | 8 |
| MINOR | 建议改进，不影响可用性 | 3 |
| INFO | 仅供人工复核，不扣分 | 0 |

评分：满分 100 起扣，下限 0。等级 A≥90、B≥80、C≥70、D≥60、F<60；退出码只由 BLOCKER（及 `--strict` 下的 MAJOR）决定，与分数无关。

## 二、逐项判据

### S · 结构与 frontmatter

| 编号 | 命中条件 | 级别 | 为什么 |
|---|---|---|---|
| S1 | 包根目录下没有 `SKILL.md` | BLOCKER | `SKILL.md` 是唯一强制文件，缺了技能无法被解析 |
| S2 | 开头没有成对的 `---` 包围 frontmatter | BLOCKER | frontmatter 不闭合，字段全部读不到 |
| S3 | frontmatter 中出现无法解析为 `key: value` 的行 | MAJOR | 该行字段会被静默丢弃 |
| S4 | 某个值为**未加引号**且内部含裸**半角**冒号（`: ` 或位于行尾的 `:`） | MAJOR | YAML 解析器（平台用 Go-YAML）会把这类值误判为映射，导致**字段整个丢失** |
| S5 | frontmatter 中带缩进的键使用了奇数个空格缩进 | MAJOR | 奇数缩进是 YAML 层级解析错的高发点 |
| S6 | `description_en` 含中文字符 | BLOCKER | 英文简介须为英文 |
| S7 | 包内存在相对路径深度 > 1 的文件（即嵌套超过「根/二级目录/文件」两级） | BLOCKER | 平台仅支持两级目录结构，深层嵌套上传报「目录层级超限」；例如 `examples/demo/bible/x.md` 会被拒。文件须放在根或一级子目录（references/ scripts/ templates/ examples/）下，可用文件名前缀区分来源 |

**已知边界**：

- S4 只对「值首字符不是引号」的情况报警；已加引号的值一律跳过。**修法是给整个值加双引号**，不是删掉冒号。
- S4/S5 的级别在 v1.1.0 由 MINOR 提升为 MAJOR：经与平台实际解析行为比对，这两类问题会让字段直接读不到，属必修项而非风格建议。
- **S4 在 v1.1.0 收窄为「只判半角冒号」**：YAML 规范里只有 ASCII `:`（后跟空格或位于行尾）是映射指示符，全角冒号 `：` 是普通字符、不参与结构解析。全库实测：真正含未加引号半角冒号的仅 **3 处**，全角冒号 **23 处**（均为「会议纪要生成：…」这类正常中文写法）。原口径（继承自 selfcheck/preflight 时期) 把全角一并判为必修，会产出 23 条假报并让上传闸门失效，故按规范与实测收窄。**若将来发现平台确实会误判全角冒号，再按证据恢复。**

|---|---|---|---|

| F3 | `version` 不是 `x.y.z` 形式 | MINOR | 版本迭代不可追溯 |
| F4 | `display_name_en` 长度 > 60 | MAJOR | 展示名超长会被截断或校验失败 |
| F5 | `name` 与目录名/包名不一致（已忽略版本后缀） | MINOR | 调用标识与路径混淆 |
| F6 | `category` 不是小写英文枚举键 | MINOR | 自由文本会归错类；判据基于同类技能的既有写法，非平台硬性枚举值 |

| F10 | 写了 `allowed-tools` 但值为空（`""` / `[]` / `null`） | BLOCKER | 声明白名单却给空值，语义矛盾 |

**已知边界**：F5 对 `chart-viz-helper-1.0.0.zip` 这类带版本后缀的包名先归一化再比较，避免把文件名当成技能名。F9 仅在 `name` 存在时判定，缺失由 F2 负责。

### C · 文档与磁盘一致性（核心）

| 编号 | 命中条件 | 级别 | 为什么 |
|---|---|---|---|
| C1 | 正文引用的 `test/...` 路径在包内不存在 | MAJOR | 声称的验证集不存在 |
| C2 | 正文引用的 `scripts/` `references/` `templates/` 等路径在包内不存在 | BLOCKER | 幽灵引用：模型会据此编造内容 |
| C3 | 上述路径出现在「举例」语境（同行含 例如/比如/示例/诸如/如␠/写进/写成 等） | INFO | 可能只是规范示例，需人工确认 |
| C4 | 配对 zip 内没有 `SKILL.md` | BLOCKER | 包不可用 |
| C5 | zip 内版本号与源码目录版本号不一致 | MAJOR | 包是旧版，交付的不是最新 |
| C6 | zip 内某文件与源码同路径文件字节不一致 | MAJOR | 包与源码已分叉 |
| C7 | zip 内存在源码没有的文件 | INFO | 可能是应交付内容或误打包 |
| C8 | zip 内缺失 SKILL.md 声明的文件（**不含**举例语境的路径） | MAJOR | 包不自包含 |
| C9 | `SKILL.md` 中含占位符（`（待补充）`/`—`）的表格行占比 > 30% | MINOR | 用空表替代输出规范，模型会照抄占位符；台账/表单类技能可忽略 |

**已知边界**：

- C3 是刻意加宽的口径。规范类技能常以示例形式提到路径（例如"接口规范应写到某个文件"），若无此豁免会产生大量假报。命中 C3 时仍需人工确认。
- 打包工具若把 QC 报告等内部文档排除在包外，属正常交付约定；此时不会命中 C7（C7 只看包内多出的文件，不看少掉的）。
- **C8 与 C3 必须同口径（v1.1.1 修复）**：C8 只针对「真实声明」的路径，举例语境（C3 已豁免为 INFO）的路径不得再升级为 MAJOR。
  触发本次修复的真实案例：`skill-dev-standard` 正文里「把接口规范**写进** `references/api-spec.md`」「建一键入口，**如** `test/run_all.py`」两处均为举例，
  单目标扫描时 C3 正确降为 INFO，但目录 + zip 配对时 C8 却复用未豁免的路径清单，产出 2 条假 MAJOR、把该技能的目录侧从 100 分打到 92 分。
  修法：在 `audit_one` 里另存 `claimed_real`（剔除举例语境），C8 只读该视图；并加夹具 `illus-skill` + 同名 zip 做回归锁死（验证集第 2b 组）。

### E · 验证证据

| 编号 | 命中条件 | 级别 | 为什么 |
|---|---|---|---|
| E1 | 正文声称 N 套件 / N 断言，但包内没有任何 `test/*.py` | MAJOR | 声明了证据却不存在的验证集 |
| E2 | 有测试脚本，但静态统计到的断言调用为 0 | MAJOR | 测试文件是空壳 |
| E4 | 某个 `.py` 语法不通过 | BLOCKER | 会在运行期直接抛异常 |

**已知边界**：断言数的精确核对必须实际运行测试，属行为层，本体检器不做。E2 只在「有声明 + 静态为 0」时触发，是零假报的保守判据。

### X · 安全

| 编号 | 命中条件 | 级别 | 为什么 |
|---|---|---|---|
| X1 | `.py/.md/.json/.txt` 等文本中出现 `键名 = "16 位以上字面量"` 形态的凭证 | BLOCKER | 密钥硬编码，须改用 `${VAR}` 占位 |
| X2 | 出现递归强删根目录或盘符、Windows 递归强删、SQL 删表、无保护目录递归删除等模式 | 见下 | 破坏性操作不可逆 |
| X5 | `SKILL.md` 中出现开发遗留标记 | MAJOR | 未完成的痕迹会随包交付 |

- **X2 分级规则**：命中位于 `scripts/` 下的可执行代码时按原级别（MAJOR/MINOR）；位于 `SKILL.md`、`references/` 等文档中时降为 **INFO**，因为文档在讲解或列举命令属正常用法。
- X2 的危险模式字面量**不在此文档重复**，以免知识文档反过来触发自身检查；权威定义见 `scripts/audit.py` 中的 `DANGER_RULES`。
- **X1 已知边界**：值中包含 your / example / placeholder / changeme / xxxx / dummy / sample / redacted / fake 等占位词时跳过，避免把模板示例判成泄漏。
- 已被"被赋值为临时目录"的变量（如 `work = tempfile.mkdtemp(...)`）再传给目录递归删除时，X2 跳过，避免把正常的临时目录清理误判成危险操作。

### D · 描述质量

| 编号 | 命中条件 | 级别 | 为什么 |
|---|---|---|---|
| D1 | 简介内容过少（中文 < 30 字，英文 < 12 词） | MINOR | 模型难以判断何时唤起 |
| D2 | 简介中没有触发场景提示 | MINOR | 触发命中率低 |
| D3 | 简介含技术实现措辞 | MAJOR | 简介应讲功能与价值，不讲怎么实现 |
| D4 | 简介含绝对化承诺用语 | BLOCKER | 不得承诺保过/保上架 |

**已知边界**：D2 中文按「触发/用于/当」判定，英文按 `use when` / `used when` / `when the user` / `trigger` 判定，避免对英文简介误报。

### G · 专家包（含 `.codebuddy-plugin/plugin.json` 的目标）

命中 `.codebuddy-plugin/plugin.json` 即按专家包体检，技能包的 S/F/C/D/E 系列不适用。

| 编号 | 命中条件 | 级别 | 为什么 |
|---|---|---|---|
| G1 | 缺少 `.codebuddy-plugin/plugin.json` | BLOCKER | 专家包必须含此配置 |
| G2 | 该文件无法解析为 JSON，或顶层不是对象 | BLOCKER | 配置读不出来，包不可用 |
| G3 | `tags` 缺失、不是数组、数量不等于 3、或某个 tag 缺 `en`/`zh` | BLOCKER | 平台要求 tags 恰好 3 个，多/少都会解析失败 |
| G4 | 缺关键字段（name / expertType / version / description / author / agents / agentName / displayName / profession / displayDescription / avatar / categoryId / defaultInitPrompt / quickPrompts） | MINOR | 影响市场展示与解析 |
| G5 | `avatar` 指向的文件不在包内、不是 PNG、尺寸不是 512×512、或体积 > 500KB | BLOCKER（无效路径/尺寸/体积）、MINOR（非 PNG/解析失败） | 头像有明确尺寸与体积要求 |
| G6 | 没有 `agents/{name}.md` | BLOCKER | 专家包须含角色定义 |
| G7 | `plugin.json` / `README` 表格或「版本：」行 / agent md（frontmatter `version` 或 H1 标题）三处版本号不一致 | BLOCKER | 版本分叉会导致包内容与声明不符 |
| G7b | 上述三处中某处**提取不到**版本号 | MINOR | 缺号会让一致性校验静默失效（缺失 ≠ 一致） |
| G7c | 包内存在**多个** `README.md`，版本校验已按最浅层（包根）取权威，其余未参与 | INFO | 混放工作区/内嵌技能自带 README 会造成歧义；只提示不判错，权威结论取打包产物 |
| G8 | `plugin.json` 文案出现「官方 / 平台客服 / 管理员 / 官方认证 / 官方推荐」 | INFO | 红线是「冒充」而非字样本身，非品牌方一律不得使用 |
| G9 | **声明的**技能路径在包内找不到 `SKILL.md`（声明缺失/非法）；另对「包内 `skills/` 目录存在但 `plugin.json` 未声明」给 INFO | BLOCKER（声明缺失/非法）；INFO（有技能却未声明） | 内嵌技能**以磁盘事实为准自动发现**（平台也按 `skills/` 目录自动发现）——「声明了却不在包内」= 断链；「有但未声明」不阻断，但建议两处对齐。⛔ 判据不得挂在「是否声明」上，否则未声明的包整段漏检（假通过） |
| G9b | 某个内嵌技能（`skills/xxx/`）内部存在相对其根深度 > 1 的文件（即该子技能目录内嵌套超过两级） | BLOCKER | 平台仅支持两级目录，内嵌技能自身同样受限；例如 `skills/xxx/examples/demo/x.md` 会被拒。须将该子技能内部子目录拍平（其根下只放一级子目录） |
| G9c | **专家包根**的 `references` / `scripts` / `templates` / `examples` 下存在二级子目录（即包内相对路径深度 ≥ 2，形如 `references/<子目录>/x.md`） | BLOCKER | 平台「仅支持两级目录」（根 / 一级子目录 / 文件）是**包级**约束，但既有判据各有各的作用对象：S7 只管**技能包**、G9b 只管**内嵌技能** → 「专家包根承载目录再嵌套」此前**无判据覆盖**（判据缺口）。实证：`pads-troubleshoot` v1.0.0 把 481 个案例放在 `references/<20 个模块>/` 下，体检器仍给 A/97 + UPLOAD GATE PASS（假通过）。修法：把二级子目录拍平到一级（模块信息可保留在文件名前缀里） |
| G10 | 内嵌技能（`skills/xxx/SKILL.md`）必填五字段不全，或 frontmatter 未闭合 | MAJOR | 内嵌技能同样要满足技能字段规范 |
| G11 | `plugin.json` 的 `skills` 与 agent md frontmatter 的 `skills` 名单不一致 | MINOR | 两处声明分叉，编排会指向不存在的技能 |
| G12 | `displayDescription.zh` 超过 **100 字** | BLOCKER | **平台上传时直接判「解析失败」**——平台校验提示：「displayDescription.zh（市场展示简介）：当前 107 字，最多 100 字」。JSON 本身合法也没用，属平台字段约束 |
| G13 | `defaultInitPrompt` 的 `zh` / `en` 与 `quickPrompts[0]` 同语言文本不一致 | BLOCKER | **平台上传时直接判「解析失败」**——平台校验提示：「defaultInitPrompt.zh 必须与 quickPrompts[0].zh 一致」。平台按字符串**全等**校验，差一个标点都拒 |
| G15 | `displayName.zh` 含平台不允许的字符（空格、全角括号等；允许集 = 中英文 + 数字 + `-` + `—`） | BLOCKER | **付费资产上传时直接拦**——平台校验提示：「付费资产的名称仅支持中英文、数字和\"-\"\"—\"，不能包含空格或特殊字符」（实证 `ad-troubleshoot` 因「Altium 排错专家」含 1 个空格被拦，2026-10-16）。影响面：全库 89 包 13 命中——付费 3（ad 空格 / coze 全角括号 / 在售 pads 空格），其余 10 个全是在售**免费**包（含空格照样过审）⇒ **规则仅针对付费资产**，本地无法区分故全包适用，在售命中按冻结纪律只标注不改 |
| G14 | `displayName.zh`（专家名称）超过 **15 字** | BLOCKER | **平台上传时直接判「解析失败」**——平台校验提示：「专家名称：当前 20 字，上限 15 字」（实证 `ad-troubleshoot` v1.0.0，原值「Altium Designer 排错专家」= 20 字）。⚠️ **平台按字符数计，英文字母逐个算 1 字**；英文名不受此限（`pads-troubleshoot` 的 en 24 字符已过审）。判据需同时覆盖 `displayName` 的 **dict 与字符串两种形态**（初版只查 dict，字符串形态静默逃逸） |
| — | 专家包同样执行 E4 语法与 X1/X2/X5 安全扫描 | 同 X/E | 专家包也会夹带脚本 |

**已知边界**：

- **zip 根目录判定（v1.2.0 修复 Z1，BLOCKER 级）**：专家包的根**以 `.codebuddy-plugin/plugin.json` 为权威标志**，优先于 `SKILL.md`。原实现取「第一个以 `/SKILL.md` 结尾的条目」为根，遇到**带内嵌技能的专家包**（`skills/*/SKILL.md`）会把根错判成第一个内嵌技能目录：整包只可见一个技能、`is_expert()` 返回 False、**G1–G8 全部漏检**。实测 `Word-Rescuer-Expert-1.0.0.zip` 有 105 个文件却只可见 14 个、`kind` 被降级为普通技能。现改为：有 `plugin.json` 即用它定根，否则取**最浅**的 `SKILL.md`（`min(cands, key=len)`）。
- **G7 提取窗口（v1.2.0 修复）**：agent md 的版本号原只扫**前 200 字符**，而实测该文件 `description` 单行即 460 字符、`v1.4.0` 在第 13 行，导致版本被静默漏检（`expert-src` 内部 1.3.1 与 1.4.0 分叉却拿满分）。现改为 frontmatter `version` 优先，否则扫 H1 标题行，再退回前 1600 字符。
- 带一层根目录的专家包 zip（如 `pkg/.codebuddy-plugin/plugin.json`）会先定位根目录再体检，不会误判为「缺 SKILL.md」。
- 专家包与技能包**不做** zip↔目录配对漂移核对（C4–C8 仅适用于技能包）。这是当前已知限制。

### T · 专家团（Team 型，`expertType == "team"`）

> **仅在 `plugin.json` 的 `expertType` 明确为 `team` 时评估**；普通 `agent` 型专家包不含这些字段，不会被 T1–T5 误伤。
> 来源：`dev-onboarding-team`（v1.0.0）实测——体检器原无任何 team 判据，该包跑出「16 项全过 / A / UPLOAD GATE PASS」，但下列结构性红线**全部未被验证**，只能靠组团任务书 §8 靠人工核验。这属于「闸门查不出 = 未来仍会漏」的盲区，故固化为判据。

| 编号 | 命中条件 | 级别 | 为什么 |
|---|---|---|---|
| T1 | `teamInfo` 缺失，或 `leadAgent`/`memberAgents` 为空，或 `members` 为空数组 | BLOCKER | 这三个字段是团队关系（主理人 ↔ 成员）的载体，缺了团队根本组不起来 |
| T2 | `agents` 声明文件名、`members[].id`、`teamInfo` 的 `leadAgent + memberAgents` 三者集合不一致 | BLOCKER | 任一处出现分叉即成员调度断链：声明了却拉不起来，或能拉起却没有成员定义 |
| T3 | `leadAgent` 为空、采用泛名 `team-lead`、或不带团队名前缀 | BLOCKER | 主理人是团队关系的锚点；泛名会让同账号下多个团队互相覆盖 |
| T4 | 缺 `settings.json`，或其 `agent` 字段未指向 `leadAgent` | BLOCKER | 平台靠该文件设定主理人；写错或缺失则团队关系建立失败 |
| T5 | `agents` 声明项写法不是 `./agents/<name>.md`，或该文件未打进包内 | MAJOR | 路径写法与可达性影响平台对成员定义的解析 |

**已知边界**：`expertType` 缺失或取其他值时，T1–T5 **一次性全部不评估**（fail-open）。这是有意为之——目前只有 `agent` / `team` 两种形态有实证样本，对未知取值强行判定会产出假 BLOCKER。

### P / I / J · 权限与交付卫生

| 编号 | 命中条件 | 级别 | 为什么 |
|---|---|---|---|
| P1 | 声明了 `Write`/`Edit`，但技能内既无 `scripts/`，正文也没有写文件/打包类动作 | MINOR | 权限过度 |
| P2 | 未声明 `allowed-tools` | MINOR | 权限边界不明确 |
| P3 | 包内含 `scripts/` 脚本，但未声明 `allowed-tools`、或声明了却未放行 `Bash` | MAJOR | 脚本运行时调不起来，技能退化为纯文本（上传闸门项） |
| I1 | `references/` 下的文件未被正文引用 | INFO | 可能冗余 |
| J1 | 存在缓存/备份/临时文件（如 Python 缓存目录、`.pyc`、`.bak`、`.DS_Store`） | MINOR | 不应随包交付 |
| J2 | `SKILL.md` 超过 800 行 | MINOR | 建议拆到 `references/` |

**已知边界（P1 在 v1.1.0 收窄）**：`Bash` 不再计入"过宽"——技能经常需要调用外部工具或**其他技能**的脚本。只有当技能声明了 `Write`/`Edit`、包内又没有 `scripts/`、正文也没有任何写文件/打包动作时，才判定为权限过度，避免把「技能开发类」技能误判成缺陷。

### L · 库级（仅在同时体检 ≥2 个目标时启用）

| 编号 | 命中条件 | 级别 | 为什么 |
|---|---|---|---|
| L1 | 多个技能的 `display_name` 相同 | MINOR | 用户无法区分 |
| L2 | 多个目标的名称归一化后相同（忽略版本后缀） | INFO | 疑似同一技能的多个副本，交付前需确认上传哪一个 |
| L3 | 多个不同技能名的首词相同且各自 ≥2 个词，且首词不在通用词头停用表内 | INFO | 命名同族，提示人工复核职责是否重叠 |

**已知边界**：

- 库级检查先按 label 去重。同一个技能常同时以「源码目录」和「交付 zip」出现，二者 label 相同，若不去重会自己和自己比较，产生大量假报。
- L3 的停用表（`skill` / `doc` / `tool` / `file` / `data` / `agent` 等）用于排除过于常见的前缀，避免把 `skill-dev-standard` 与 `skill-quality-audit` 这类"名字都带 skill 但职责不同"的组合当成可疑项。

## 三、行内抑制

任一行包含 `audit-ignore` 时，该行不参与 X1 / X2 / X5 等内容类扫描。用于「文档本身就在讲解这条规则」的场景。

## 四、上传闸门（`--profile upload`）

`--profile upload` 把体检结果收敛为一道**是否允许上传**的硬闸门，命中下列任一编号即 EXIT 1：

- 结构：S1、S2、S4、S5、S6、S7
- 必填与写法：F1、F4、F7、F8、F9、F10、F11、F12
- 简介质量：D3、D4
- 幽灵引用与包漂移：C2、C4、C5、C6、C8
- 凭证与语法：X1、E4
- 权限与交付卫生：P3
- 专家包：G1、G2、G3、G5、G6、G7、G9、G9b、G9c、G12、G13、G14、G15
- 专家团（仅 `expertType=team` 时评估）：T1、T2、T3、T4、T5

口径来源：**原 `selfcheck` 的全部 5 项 ∪ 原 `preflight` 的全部必修项**。两个旧脚本的能力已全部并入本体检器，旧脚本已归档。

闸门**故意比全量体检严**：全量体检看「有没有阻断项（BLOCKER）」，闸门看「有没有必修项」，因此同一技能可以全量通过、闸门拦下（典型例子：`display_name_en` 超长是 MAJOR，全量不阻断、闸门拦住）。

## 五、不作为的部分

- 不判断文档措辞是否优美、结构是否合理——那是人读出来的。
- 不判断技能的实际效果好不好——那要跑行为测试。
- 不判断触发词是否"最合适"——只判断有没有。
- 不判断两个技能职责是否真的重叠——L3 只给同族提示，结论由人下。
